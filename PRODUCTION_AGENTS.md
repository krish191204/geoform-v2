# Production agents

Geoform is being productionized by a small fleet of specialised agents that each own a disjoint slice of the repository. The intent is to avoid edit conflicts and let work proceed in parallel: every agent knows exactly which paths it can touch, and any path outside its ownership is *out of scope*.

## Overview

The productionization effort is split across:

- **Docs agent** — `README.md`, `PRODUCTION_AGENTS.md`, and any new files under `docs/` except `docs/contract.md`.
- **Frontend agent** — the TypeScript SPA under `src/`, plus `index.html`, `public/`, `vite.config.ts`, `vitest.config.ts`, and `tsconfig.json`.
- **Backend agent** — the FastAPI service under `server/api/`, the bridge at `server/worldengine_api.py`, `server/run_dev.sh`, and `pyproject.toml`.
- **Infra agent** — `Dockerfile`, `Dockerfile.dev`, `docker-compose.yml`, `.dockerignore`, `Procfile`, `.github/`, `scripts/`, and `.env.example`.
- **Tests agent** — `tests/` (Python) and colocated `*.test.ts` files under `src/` (only when adding new test files).

Each agent modifies only its owned paths. If an agent needs a change outside its scope, it must request the owning agent to make the change — agents never silently rewrite another agent's files.

## Parallel batching rules

1. **Disjoint edits.** Two agents may work in parallel only if their changes do not touch overlapping files. Overlapping edits are merged serially by the orchestrator.
2. **Touch the smallest set.** When an agent's task can be solved by editing one file, edit one file. Don't refactor across the boundary.
3. **No drive-by changes.** An agent must not "fix" something outside its scope while doing its own work. Open a follow-up instead.
4. **Tests follow code.** When the frontend or backend agent changes behaviour, the tests agent updates the colocated tests in the same batch — not after the fact.
5. **Docs follow API.** When the backend agent edits `docs/contract.md`, the docs agent must not also rewrite the README's API summary in the same commit; one source of truth per change.
6. **Atomic commits.** Each agent's batch lands as one commit (or one PR) with a single concern. Do not stack unrelated fixes.

## Adding a new agent / splitting an existing one

When a slice of the codebase grows enough to warrant its own owner:

1. **Propose the boundary.** Write a short note describing the new path prefix and what it displaces from the current owner.
2. **Update this file.** Add the new agent's owned paths to the table above, and remove them from the previous owner's row.
3. **No silent overlap.** The previous owner must explicitly hand off the files — the new agent's first commit should reference the hand-off.
4. **Keep the table exhaustive.** Every non-generated file in the repo must appear in exactly one row. If a file has no natural owner, the orchestrator assigns it.
5. **Test the boundary.** Run `find src server tests -type f` and confirm the new table covers everything.

When an agent retires (its slice is empty or its job is done), mark it dormant in this file but keep the row so historical commits remain attributable.
